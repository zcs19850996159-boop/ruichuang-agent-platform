# 第一阶段量化验收门禁

第一阶段交付的是模块化单体和可复现发布，不是 WorkBuddy、MCP 或云端多租户产品。所有实时请求继续经过同一个客服核心，正式接口保持 `POST /chat` 与 `POST /chat/stream`。

## 1. 基线冻结

必须同时具备：

- 完整源码与知识资产归档；
- 归档 SHA-256 与逐资产 Manifest；
- Python 依赖锁文件；
- 应用、知识、模型配置、Prompt 四类版本；
- 环境变量模板（不含密钥）；
- 历史性能基线与回归结果；
- Git Commit 与不可变 Tag。

Docker 镜像只在具备 Docker/BuildKit 的构建机上生成；发布记录必须写入镜像 Digest。没有构建能力时不得伪造 Digest，应明确标记为待 CI 构建。

## 2. 功能回归

| 回归集 | 门禁 |
|---|---|
| 官方 API 契约 | 通过率 100% |
| 400 题冻结集 | API（允许基础设施错误隔离重试后）、路由、手册、约束和 `<PIC>`/图片数量通过率 100% |
| 人工修复关键题 | 通过率 100% |
| 图片题 | 图片精确集合/顺序通过率不低于冻结参考的 99.5%，平均 F1 不低于 0.9991 |
| 无证据请求 | 不得增加无依据回答；必须保持澄清或拒答策略 |

外部模型的 429、5xx 或网络超时单独记录为基础设施错误；在相同输入、单并发重试通过后，不计为确定性功能退化，但必须进入错误率报告。

以上冻结参考来自 `full400_followup_valid_merged_20260724_summary.json`。若更换参考集或评分器，必须创建新基线，不能把不同口径的结果直接比较。

## 3. 性能门禁

固定测试条件：

- 相同服务器、CPU/GPU 和网络；
- 相同模型、知识版本、Prompt 版本与索引；
- 预热后测试；
- 明确是否启用答案缓存；
- 分别测试单并发、并发 5、并发 10；
- 文本与图片使用固定输入；
- 同时记录 P50、P95、首字、错误率和超时率。

目标：

| 指标 | 第一阶段目标 |
|---|---:|
| 纯文本完整 P50 | ≤ 6 秒 |
| 纯文本首字 P50 | ≤ 2.5 秒 |
| 图片完整 P50 | ≤ 15 秒 |
| 图片首字 P50 | ≤ 7 秒 |
| 图片完整 P95 | ≤ 30 秒 |

如果外部模型波动导致目标不能复现，报告必须拆分选择、检索、证据构建、视觉、模型生成和校验阶段，不以总时延掩盖瓶颈。

## 4. 架构门禁

- 新入口只能调用 `CustomerServiceApplication`；
- 比赛实现只能通过 `compatibility` 适配器进入；
- 模块间不增加内部 HTTP；
- 请求上下文包含租户、知识空间、权限和四类版本；
- 缓存键绑定租户、知识空间、权限、Profile 和四类版本；
- Enterprise Profile 不能由请求启用 Competition 补丁；
- 不在实时请求中重载知识资产、写选择器临时文件或修改进程级环境变量。

## 5. 第一阶段不包含

- WorkBuddy Skill 与 MCP 发布；
- 自动手册摄取、审批与原子发布；
- 企业多租户控制平面；
- 题目补丁一次性 YAML 化；
- 多 Agent 实时客服链路。

这些能力分别属于第二、第三阶段，第一阶段仅预留稳定应用接口、请求上下文和版本边界。
